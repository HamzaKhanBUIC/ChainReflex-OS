Since you are planning to aggressively use AI and "vibe coding" (directing AI to write the bulk of the code while you orchestrate the logic), your strategy has to shift entirely.

As a judge, I can usually spot a team that let an AI "write the whole thing" because the code becomes a tangled, unscalable mess that breaks during the live demo. Vibe coding is a massive competitive advantage, but only if you act as the strict Lead Architect, treating your AI coding tools as junior developers who need very precise, isolated tasks.

Here is my expert playbook for executing a globally competitive AMD ROCm project using an AI-assisted vibe coding workflow:

1. Defeat the "CUDA Bias" in Your AI
Most coding LLMs (like Claude 3.5 Sonnet, GPT-4o, or Cursor) were trained on mountains of NVIDIA/CUDA documentation. If you just ask them to write GPU-accelerated PyTorch code, they will default to CUDA, and it will crash on the AMD Developer Cloud.

The Fix: Create a "System Prompt" for your coding sessions. Explicitly tell your AI: "We are deploying on AMD MI-series GPUs using ROCm. Do not use cuda:0 or NVIDIA-specific libraries. Ensure all PyTorch device allocations use standard agnostic methods (e.g., device = torch.device('cuda' if torch.cuda.is_available() else 'cpu') which ROCm aliases correctly) or explicitly use AMD HIP equivalents where necessary. Prioritize vLLM for serving."

Provide Context: Feed your AI the latest AMD ROCm and vLLM-ROCm documentation directly into its context window before asking it to build the pipeline.

2. Isolate and Conquer (Modular Vibe Coding)
If you prompt your AI to "build an autonomous supply chain agent," it will hallucinate a massive, broken file. You must break the architecture into microscopic pieces.

Define the "Contracts" First: Have the AI write the schemas (Pydantic models or JSON structures) for how data moves between your agents.

Build Micro-Scripts: Prompt the AI to build one thing at a time.

Prompt 1: "Write a standalone Python script that takes a hardcoded string and runs it through Llama-3 locally using vLLM." (Test it, confirm it works).

Prompt 2: "Write a standalone script that searches the SerpAPI for news and returns a JSON." (Test it).

Prompt 3: "Now, write a LangGraph flow that connects script 1 and script 2."

Why this wins: If something breaks during the hackathon, you know exactly which 50-line module failed, rather than digging through 2,000 lines of AI-generated spaghetti code.

3. Aggressive Version Control
Vibe coding moves so fast that you can have a working app at 2:00 PM, ask the AI to "add one quick feature," and have a completely broken app at 2:05 PM.

Commit religiously: Every time the AI generates a block of code that actually runs, immediately commit it to Git.

Branch for experiments: If you want the AI to attempt a complex integration (like the Docker sandbox for Idea 2), create a new branch. Do not let the AI rewrite your stable main branch.

4. Mock the Periphery, Build the Core
You only have a few days. The judges care about your innovative use of AMD hardware and open-source models, not whether your frontend login page looks pretty or if your Twilio account is fully funded.

Tell the AI to mock the boring stuff: "Write a function that simulates buying insurance on the blockchain by printing a success message and returning a dummy transaction hash."

Focus the AI on the 'Wow Factor': Spend 80% of your vibe-coding energy on the core agent loop—making sure the LLMs running on ROCm are talking to each other intelligently, handling errors, and executing the autonomous logic perfectly.

5. Use the "Rubber Duck" Debugging Technique
When the code inevitably crashes on the AMD stack, don't just paste the error into the AI and say "fix this." That leads to infinite hallucination loops.

Read the stack trace: Find exactly where it failed.

Prompt precisely: "The code failed at the vLLM initialization on the MI300X. Here is the specific memory allocation error: [Paste Error]. Look at the arguments we passed to the EngineArgs. How do we adjust the gpu_memory_utilization or tensor_parallel_size for an AMD environment to fix this?"
